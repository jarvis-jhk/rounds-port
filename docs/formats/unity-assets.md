# unity-assets: how the game's data is read

## SerializedFile (format 22, Unity 2022.3)

`crates/unity/src/serialized.rs`.

**Header** (big-endian):

- legacy `u32` metadata size, `u32` file size, `u32` format, `u32` data offset
- `u8` endianness, then 3 reserved bytes
- format ≥ 22 only: `u32` metadata size, `i64` file size, `i64` data offset,
  `i64` reserved

**Metadata** (little-endian in this build):

- Unity version string, `i32` platform, `bool` type-tree flag (false in
  player builds)
- types: `i32` class id, `u8` stripped, `i16` script type index, a 16-byte
  script hash for MonoBehaviours, a 16-byte type hash
- objects: aligned to 4, then `i64` path id, `i64` byte start, `u32` size,
  `i32` type index
- script types: `i32` file index, aligned `i64` path id. These are PPtrs to
  `MonoScript`s.
- externals: empty string, 16-byte GUID, `i32` type, path
- reference types: same layout as the types
- user info string

**PPtrs**: `file_id` 0 is the same file. `file_id` n points into
`externals[n-1]`, resolved by file name inside `ROUNDS_Data` (or
`ROUNDS_Data/Resources` for `unity default resources` and
`unity_builtin_extra`).

## Type trees

The build ships without type trees, so we embed them:

- `crates/unity/typetrees/engine.json`: every engine class in the game files,
  taken from UnityPy's TPK database for 2022.3.34f1.
- `crates/unity/typetrees/scripts.json`: every MonoBehaviour class used by the
  data (386), generated by TypeTreeGenerator from the game's DLLs, plus the
  `[SerializeReference]` payload classes (`ref_types`). Script entries hold
  only the fields after the MonoBehaviour header. The reader prepends the
  engine header, which aligns after `m_Enabled`; the generator's header does
  not.

Both files hold only layouts (field names, types, alignment flags), no data
from the game's assets. To regenerate them:

```
python -I scripts/dev/gen_typetrees.py
```

Each node is `[level, type, name, (byte_size,) meta_flags]`, listed in
pre-order. The interpreter (`typetree.rs`) follows Unity's binary rules:

- Primitives are stored unaligned.
- `string` is an `i32` length followed by the bytes, then always aligned.
- A node whose first child is `Array` is an array: an `i32` count, then that
  many elements. `UInt8`/`char` arrays become bytes.
- `TypelessData` is an `i32` length followed by raw bytes.
- Meta flag `0x4000` on a node, or on its `Array` child, aligns the stream
  to 4 bytes afterwards.
- `ReferencedObjectData` payloads are typed by the sibling
  `ReferencedManagedType`.

TypeTreeGenerator labels `string[]` fields as `string` with an `Array` of
strings beneath, so a `string` node counts as a plain string only if its
array holds `char`.

**Validation**: `cargo run --release -p unity-assets --example validate`
reads every object of every file (120,248 objects) and compares the results
with `ref/dump` (UnityPy). Result: every object consumes exactly its stored
size, except the `GlobalSerializationConfig` editor asset, and there are 0
value mismatches. 8 objects have no usable UnityPy reference because
UnityPy itself fails on them; we read those exactly too.

## Asset bundles (`bundle.rs`)

Only the localisation bundles in `StreamingAssets/aa/` are read. `UnityFS`
container: big-endian header (`"UnityFS"`, format version, Unity version
and revision strings, total size, compressed/uncompressed block-info size,
flags: bits 0-5 compression of the block info, `0x80` block info at the end,
`0x200` data aligned to 16), aligned to 16 for format >= 7; block info = a
16-byte hash, block table (uncompressed size, compressed size, flags) and
node table (offset, size, flags, path) into the concatenated decompressed
blocks. Compression 2/3 (LZ4/LZ4HC) is an LZ4 block without frame, decoded
by our own `lz4_block`; LZMA is not supported (unused).

The SerializedFiles inside bundles embed type trees: per type a blob (`i32`
node count, `i32` string-buffer size, 32-byte node records `u16` version,
`u8` level, `u8` flags, `u32` type-name offset, `u32` name offset, `i32`
byte size, `i32` index, `u32` meta flags, `u64` ref-type hash, then the
string buffer; offsets with the high bit set index Unity's built-in string
table, `common_strings.rs`), followed by the type dependencies (format >=
21), or for reference types the class, namespace and assembly names.
`read_embedded` decodes every object with those trees, `[SerializeReference]`
payloads with the file's reference types.

## Textures

`texture.rs` decodes the first mip level to RGBA8 and flips the rows so
they run top-down. Supported formats: DXT1, DXT5, BC4, BC5, RGBA32, ARGB32,
BGRA32, RGB24, RGB565, ARGB4444, RGBA4444, Alpha8, R8 and RG16. Image data is
inline (`image data`) or in `m_StreamData` (`.resS`).

## Audio: FSB5 Vorbis → Ogg

`audio/`. `AudioClip.m_Resource` points into `.resource` files, each slice
being an FSB5 bank with one Vorbis sample:

- **Bank header**: `"FSB5"`, version, counts, section sizes, codec (15 =
  Vorbis), padded to 60 bytes (version 1) or 64 bytes (version 0).
- **Sample header**: a `u64` bit field holding the frequency index, the
  channel code, the data offset / 32 and the sample count, followed by
  chunks. Chunk 11 holds the CRC32 of the Vorbis setup header, which FMOD
  stripped.
- **Sample data**: `u16` packet length followed by the packet, repeated.

The remux:

1. Build the Vorbis identification header (block sizes 256 and 2048) and a
   comment header.
2. Look up the setup header by CRC32 in `data/fsb5_vorbis_setup.bin`: 161 FMOD
   setup headers converted from the MIT/Apache-2.0 `fsbex` crate by
   `scripts/dev/gen_fsb_vorbis_setup.py`. This is FMOD codec data, not game
   content.
3. Parse the setup header's mode table, using a small forward parser over
   codebooks, floors, residues and mappings.
4. Compute granule positions from each packet's block size. A packet adds
   prev/4 + cur/4 samples, and the first packet adds none. The final granule
   is clamped to the FSB sample count.
5. Write Ogg pages of about 4 KiB.

The audio is never re-encoded. We did not use `fsbex` itself: it decodes and
re-encodes through libvorbis (C, lossy).

**Validation**: `cargo run --release -p unity-assets --example audio_check`
converts all 1032 clips. Every file decodes with lewton, with matching
channels and rate. The last granule equals the FSB sample count, which equals
`m_Length × rate`. ffmpeg also decodes the files without errors. Note that
ffmpeg reports 128 fewer samples for single-page files; it does the same for
libvorbis-encoded reference files.
